# PhotoTok — Requirements

> Product: **PhotoTok** (`products/android/phototok/`, Gradle module `:phototok`, package
> `com.phototok`). Target: phone form factor (< 600 dp), portrait, gesture-first.
> Scope: this file is authoritative for the PhotoTok app only. PhotoTok deliberately
> excludes OpenCV analysis, the Room score cache and Vico charts to stay lightweight —
> see [`../../shared/FEATURE_PARITY.md`](../../shared/FEATURE_PARITY.md).
> Android platform baseline: [`../../shared/ANDROID_PLATFORM.md`](../../shared/ANDROID_PLATFORM.md).
> Visual design: [`DESIGN.md`](DESIGN.md). Architecture: [`ARCHITECTURE.md`](ARCHITECTURE.md).

## 1. Feature Set & Exclusions

PhotoTok may additionally omit:
*   Focus Mode / side-by-side comparison view (not practical on small screens).
*   Detailed EXIF metadata panel (accessible via tap-to-expand on phone).

PhotoTok includes:
*   **Picture Randomization:** A toggle in settings allows users to randomize the order of pictures shown in the viewer. Enabling this setting shuffles the loaded pictures and overrides orientation-based sorting.

## 2. Gesture & Touch Interaction

    - **PhotoTok:** Vertical swipe via `VerticalPager` (up/down) to navigate between images in the feed, and horizontal swipe gestures for the configured copy/move/delete actions.
    - **PhotoTok:**
      - Pinch-to-zoom (two fingers) and double-tap zoom (to 2.5x) are supported.
      - When zoomed in (`scale > 1.05f`), dragging with a single finger pans/moves the image frame, constrained within image boundaries so it does not go off-screen.
      - While zoomed, normal swipe gestures (vertical paging scroll and horizontal keep/discard swipes) and navigation peeks are disabled to prevent conflicts and visual edge artifacts.
      - Resetting zoom (double-tapping again, or pinch-releasing below the `1.05f` threshold) smoothly animates the scale and offset back to fit-screen size and re-enables swiping mode.
*   **Selection/Deletion:** Long-press for context menu. Swipe gestures configurable. On the PhotoTok, swiping left defaults to a non-blocking temporary deletion where the image is immediately hidden from the viewer and a "Revert Deletion" button is shown. Navigating away from the current image or leaving the viewer finalizes the deletion and deletes the file via SAF. Before putting the image into the temporary deletion state, the **Direct Delete Confirmation** dialog is shown. It does not have a checkbox in the dialog, but hints that it can be disabled in settings. In settings, this **Direct Delete Confirmation** option is offered with a warning indication.
    - The revert option is preserved immediately after confirmation.
    Alternatively, in settings, the user can configure a different behavior for the left swipe: Copy to Custom Folder or Move to Custom Folder, matching the behavior of the right swipe. When configured as Copy or Move, the operation is executed immediately (showing a success feedback message and an action icon flash animation) and targets a user-defined folder. If no custom folder is selected, it defaults to a subfolder named `"PhotoTok_LeftSwipe"` inside the source folder.
*   **Non-Blocking Copy/Move (PhotoTok):** A copy or move must never make the user wait on file I/O. The feed is updated **optimistically the moment the gesture completes** — a move drops the photo (and its included siblings) out of the feed, a copy advances to the next photo — and the transfer then runs on the injected application-scoped `CoroutineScope` (`@ApplicationScope`) so it also completes if the user leaves the screen immediately after swiping. Because the feed is ahead of the file system, failure handling is mandatory: any file that did **not** actually move is re-inserted at its original position in both the filtered and unfiltered lists, and the failure is reported as error feedback. The re-insertion tracks the active photo by URI (`com.phototok.domain.OptimisticFeed`), never by index, so restoring a photo cannot silently shift the user onto a different one. A failed *copy* leaves the feed alone — the source file never left. The `ViewerBottomBar` "Revert" affordance continues to cover deletions only.
    For other clients or operations, delete uses Snackbar with Undo (30s) or confirmation dialogs.
*   **First-Run Action Explanations (PhotoTok):** Because the phone client is gesture-first, the *effect* of an action is invisible unless stated. The first time the user performs each action (swipe right, swipe left in either delete or copy/move mode, single tap, double tap, first vertical page change, first revert) the app shows a dismissible explanation card describing what just happened and pointing at the relevant setting — e.g. "You copied this photo to Keepers. Every swipe right does the same. You can change this in Settings." Each explanation fires exactly once; the seen-keys are persisted in DataStore (`seen_first_run_hints`). Wording is produced by the pure `com.phototok.domain.FirstRunHintText` from the user's *current* settings, so it always reflects the configured verb (copy vs. move) and the configured target folder. Explanations are suppressed while the full-screen tutorial is visible, and auto-dismiss after 7 seconds.
*   **Swipe Indicator Labels (PhotoTok):** The mid-swipe indicator must name the action the user has *configured*, never a default or a euphemism. Swipe right is labelled `COPY` or `MOVE` from `CollectionAction` (it must never read "KEEP" — the photo is filed into the collection folder, and under `MOVE` it leaves the source folder entirely); swipe left is labelled `COPY`, `MOVE` or `DELETE` from `SwipeAction`. Icons match the label (copy / move / trash) in the mid-swipe indicator, the post-action flash and the first-run idle "peek" hints, and the accessibility description names the destination folder. All of this wording lives in the pure `com.phototok.domain.SwipeLabels` so the viewer, the peeks and the controls guide cannot drift apart.
*   **Controls Guide (PhotoTok):** A help button in the viewer (portrait top app bar and landscape left side panel) toggles a **coach-mark overlay**, not a list. It dims the viewer and labels the controls where they actually are: callouts with short leader lines sit directly under the top app bar (logo → camera info, help, settings) and directly above the bottom bar (Sources, Selection, Revert), while the centre animates the three swipe directions — up/down for paging, left and right captioned with the configured actions and target folders — around a photo-shaped frame that carries the single-tap and double-tap/pinch hints. Everything fits on one screen: the guide must not scroll. It must not claim controls that do not exist (there is no camera symbol; the EXIF overlay is toggled by tapping the app logo), and it is parameterised by the configured swipe actions and folder names so it can never describe a left swipe as "delete" when the user has configured copy or move. The same composable serves the first-launch tutorial. A "Reset Tutorials" entry in Settings clears the seen-hint keys and the tutorial timestamp so all guidance reappears.
*   **Gesture Tutorial Overlay:** The overlay reserves the height of the real top app bar and bottom bar (`TOP_BAR_HEIGHT` / `BOTTOM_BAR_HEIGHT` in `GestureTutorialOverlay.kt`, kept in sync with `PhoneModeScreen` and `ViewerBottomBar`) and the bars therefore stay visible above the scrim — the coach marks exist to label those buttons, so hiding them would defeat the guide. Nothing may overlap: the callouts sit inside the reserved bands, and the dismiss button sits above the bottom callouts. The overlay container must apply status bar and navigation bar padding to prevent clipping by system decorations. The first-run explanation cards remain suppressed while the overlay is visible.

## 3. Architecture Conventions

*   **Typed Settings:** User-facing choice settings are typed enums in `com.phototok.domain` (`SwipeAction` delete/copy/move, `CollectionAction` copy/move, `FileTypeFilter` all/raw/jpg). Raw strings must not be passed through ViewModels or UI; the DataStore wire format is the enum's `key` (backward compatible with previously persisted values).
*   **Typed Settings Flow:** All simple phone-mode settings are exposed by `SettingsRepository` as one typed flow (`phoneSettings: Flow<PhoneSettings>`) mapped from the single DataStore `Preferences` snapshot. ViewModels must collect this flow instead of `combine`-ing individual setting flows with positional array casts.
*   **Image Source Abstraction:** Every image backend implements `com.phototok.data.source.ImageSource` (currently only `LocalImageSourceImpl` for SAF/DocumentFile; SAF document providers also cover cloud storage such as Google Drive, so no dedicated remote backend exists). URI-scheme dispatch for per-image operations happens exclusively in `ImageSourceResolver`/`ImageRepositoryImpl`; ViewModels and UI must not branch on URI schemes. Cross-source copy/move is rejected by the repository. Adding a new backend means one new `ImageSource` implementation plus registration in the resolver.
*   **ViewModel Boundaries:** ViewModels must not hold `Context` or data-source clients. Folder-name resolution and permission persistence go through `ImageRepository.prepareSourceFolder`/`resolveFolderName`. The read-only selection viewer is backed by its own `SelectionViewerViewModel` (listing via `ImageRepository.listSelectionImages`).
*   **Pure Domain Logic:** List/ordering logic must live in `com.phototok.domain` free of Android dependencies so it is unit-testable: `PhoneFeedOrdering` (ordering, file-type filtering, portrait-split computation, progressive batch de-duplication and append), `PendingDeleteLogic` (pending-delete/revert list transitions), `OptimisticFeed` (recording feed slots and re-inserting files whose copy/move failed), `RelatedFiles` (sibling detection), `PhotoExtensions` (single source of truth for RAW/JPEG extension sets), `PhotoFolders` (app-managed folder names), `CopyMoveFeedback` (copy/move feedback messages incl. partial failures), `SwipeLabels` (swipe indicator and coach-mark wording).
*   **Pending Deletion Lifecycle:** Finalizing a pending deletion (primary image AND its related siblings) must run on the injected application-scoped `CoroutineScope` (`@ApplicationScope`), never on an ad-hoc scope, so deletions complete even when the ViewModel is cleared mid-undo-window.
*   **Folder Discovery:** Only one image-discovery collection may be active at a time; selecting a new source folder cancels the previous discovery `Job` (and the dimension-loading `Job`) and clears the published-URI set and the current feed, so batches from a new folder cannot be appended to a stale one.
*   **Progressive Folder Discovery (time-to-first-swipe):** `ImageSource.discoverImages` must emit **progressively**, not once at the end: a first batch after `LocalImageSourceImpl.FIRST_BATCH_SIZE` (24) photos, then every `BATCH_SIZE` (250), then a final complete snapshot. Emissions are cumulative. Opening a folder with thousands of photos must therefore let the user swipe within a fraction of a second, with the viewer replacing the loading screen on the first batch and `PhoneModeUiState.isDiscovering` telling the UI the count is still growing (rendered as a trailing `+` on the page counter).
    - **One query per directory:** the walk is an iterative breadth-first traversal driven by `ContentResolver.query` on `DocumentsContract.buildChildDocumentsUriUsingTree`, selecting document id, display name, MIME type, size and last-modified in a single cursor per folder. `DocumentFile.listFiles()` plus its per-attribute getters must not be used for enumeration: each attribute is a separate binder round-trip (~5 per file), which is what made large folders take tens of seconds. A single unreadable directory is logged and skipped, never fatal.
    - **Append-only merge:** the ViewModel merges each batch with `PhoneFeedOrdering.newItems` (de-duplicate against every URI ever published for this folder, so a photo the user already moved or deleted is not resurrected) and `PhoneFeedOrdering.appendBatch` (order/shuffle the new batch only and append it). The already-visible feed must never be reordered mid-load. With randomization on this means the feed is shuffled per batch rather than globally — an accepted trade-off, since photos moving under the user's thumb is worse.
    - **Deferred position restore:** a saved per-folder position beyond the loaded range is clamped to what is available and re-applied as further batches arrive, until it is reached or the user changes page themselves (which cancels the restore).
    - **Dimension loading:** the dimension pass is not cancelled and restarted per batch; a run already in flight is left alone and each URI is read at most once, with a final forced pass when enumeration completes.
*   **File Copies:** A failed copy must not leave a zero-byte or partially written destination file behind.
*   **Copy/Move Feedback:** Copy/move actions track each file's result individually: only successfully moved files stay out of the feed (see **Non-Blocking Copy/Move** in §7.4 — removal is optimistic and reversed on failure), and partial failures are reported ("Moved 1 of 2 …, 1 failed") as error feedback.
*   **State Update Batching:** Asynchronously loaded image dimensions are applied to the UI state in batches (`PhoneModeViewModel.DIMENSION_BATCH_SIZE`), not per image, to bound recompositions in large folders.
*   **Per-Folder Positions:** Last-viewed positions are stored under URI-keyed preferences (`folder_pos_v2_<uri>`; legacy `hashCode`-based keys are read as fallback and cleaned up on write). When a folder is evicted from the recents list, its stored position is removed so the preferences file does not grow unboundedly.
*   **No Dedicated Cloud Integration (SAF ONLY):** PhotoTok must not integrate cloud storage SDKs or APIs directly (no Google Sign-In, no Drive REST client, no Google Picker, no OAuth scopes). Cloud storage is reached exclusively through the Storage Access Framework: the system folder picker (`ACTION_OPEN_DOCUMENT_TREE`) exposes cloud document providers (e.g. Google Drive) alongside local storage, and the resulting tree URIs behave like any other SAF source. Rationale: a generic single code path, no restricted-scope verification / CASA assessment, no GMS dependency, and no `INTERNET` permission — the app performs no network I/O of its own.
*   **Legal Links (Play compliance):** The settings screen must expose "Privacy Policy" and "Legal Notice (Impressum)" links (Google Play requires an in-app privacy-policy link; the Impressum addresses § 5 DDG). The public URLs live in `com.phototok.domain.LegalLinks` (single source of truth); the documents themselves are maintained in `docs/products/phototok/` and hosted publicly (see `docs/products/phototok/RELEASE_CHECKLIST.md`). The privacy policy documents the on-device processing model and must be updated when it changes.
