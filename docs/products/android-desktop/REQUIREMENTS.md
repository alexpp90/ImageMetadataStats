> Product: **Android Desktop** (`products/android/android-desktop/`, Gradle module `:android-desktop`, package
> `com.photoselectortoolbox`). Target: Samsung DeX, large tablets (≥ 840 dp), Chromebooks.
> Scope: this file is authoritative for the Android Desktop app only.
> Requirements it shares with PhotoTok (Android platform baseline, EXIF, storage) live in

## 1. Platform Targets & Tech Stack

*   **Primary Targets:** Samsung Galaxy Tab S11 Ultra (tablet), Samsung Galaxy S25 Ultra with DeX (desktop mode). The application must provide a feature-rich experience on large screens (≥840dp) that approaches desktop parity.
*   **Secondary Target:** Phone form factor (<600dp) with a streamlined UI optimized for touch-first interaction.
*   **Language & Framework:** Kotlin 2.0+ with Jetpack Compose and Material Design 3.
*   **Architecture:** MVVM with Clean Architecture (UI → ViewModel → UseCase → Repository → DataSource). All layers are separated by interfaces.
*   **Async Model:** Kotlin Coroutines with Flow for reactive data streams. Use `Dispatchers.IO` for file I/O, `Dispatchers.Default` for CPU-intensive analysis. Never block the main thread. Work that must outlive the screen that started it — an optimistic transfer still running after the frame has gone, a deferred deletion committed after the selector is left — runs on the `@ApplicationScope` `SupervisorJob() + Dispatchers.IO` scope provided by `di/CoroutineModule`, never on `viewModelScope`.
*   **Repository Contract:** File operations return `FileOperationResult` (source URI, destination URI, success, error) — never `Boolean`, which discards where the file went and makes undo impossible below the UI. `MoveToSelectionUseCase.MoveResult` is an alias of that one type, so the product has a single result shape. Callers above the repository must never branch on a URI scheme, and must never reach past the interface for a storage API of their own: `ImageRepository.openFolder(context, uri)` persists the permission grant and confirms the folder resolves, returning its display name or `null`. `DocumentFile` and `takePersistableUriPermission` appear nowhere above the repository — when they did, the tests had no way to open a folder without a real SAF grant and both suites adopted a second URI scheme to skip past it, testing the discovery path by avoiding the branch that reaches it. `undoMove` returns a moved file to the opened folder without sorting; SAF exposes no parent lookup, so the file returns to that folder's root rather than to its original sub-folder, and the limitation is stated on the interface rather than hidden.
*   **~~A Drive Move Relocates the File, It Does Not Link It~~ (deprecated 2026-08-08):** Removed with the Google Drive source. See *No Network Access* below.
*   **No Network Access:** This product declares **no Android permissions at all**, `INTERNET` included, and depends on no Google Play Services library. Every photograph is read through the SAF grant the photographer hands over, all analysis is on-device (OpenCV via JNI, the aesthetic model from assets), and nothing is uploaded. The Google Drive source that once required `INTERNET`, `play-services-auth` and a **restricted** `auth/drive` OAuth scope is removed: SAF already mounts Drive as a directory, so the second source duplicated the mount while carrying the whole cost. A `last_folder_uri` persisted under the retired `gdrive://` scheme is dropped on read (`SettingsRepository.RETIRED_DRIVE_SCHEME`) rather than handed to the selector, which would report "permission revoked" on a folder the photographer never lost.
*   **Dependency Injection:** Hilt for all injectable classes.
*   **Android SDK:** minSdk 26, targetSdk 36, compileSdk 36.

## 2. Adaptive Layout Requirements

*   **Window Size Classes:** Every screen must support three `WindowWidthSizeClass` breakpoints:
    *   **Compact (<600dp):** Single-pane layouts, BottomNavigation, simplified controls, swipe-based navigation.
    *   **Medium (600–840dp) and Expanded (≥840dp):** A labelled left sidebar and **one** comparison layout — three equal frames arranged **one over two**, the Current frame centred with its named metric readouts to its left and its controls to its right, Previous and Next centred as a pair beneath it. There is no second comparison layout, no layout toggle, and no top app bar.
    *   **Frame Size Is the Binding Requirement:** Three equal frames arranged *in a row* are width-bound and cap at 493×370dp while abandoning ~60 % of the display's height; arranged one over two they are height-bound and reach 600×450dp for 4:3 images and 675×450dp for 3:2 images on the reference device (1480×924dp). The row arrangement is therefore prohibited. Frame size is computed **once** per composition from both constraints and the active image's aspect ratio (defaulting to 3:2 for standard camera resolutions like 6192×4128, or 4:3), with side flank widths dynamically computed from remaining top-row space down to a 260dp baseline. The same `DpSize` is handed to all three tiles — never via a per-tile `aspectRatio` modifier, whose default width-first resolution lets frames of different orientations resolve to different heights. **Which axis binds depends on the photograph, and this must not be assumed:** measured on the reference device, 4:3 gives 600×450 and 3:2 gives 675×450 with the *height* binding, but 16:9 gives 684×385 with the *width* binding — two 16:9 frames abreast want 1464dp of a 1376dp region, so 385dp is the ceiling of the display and freeing height does not move it. A UI test asserts all three frames are identical to within the border delta; a second re-derives the frame from the measured window through `FrameGeometry.imageRegion` + `threeUpLayout` and asserts the drawn frame matches, which fails for any chrome that enters the vertical stack at any window size or aspect ratio. A fixed "≥45 % of the window height" is **not** a valid form of that assertion — it reported the 16:9 ceiling as a defect on every window it was run on.
    *   **Chrome Placement Follows the Binding Constraint:** On this layout height is scarce and width is surplus (~124dp per frame at 4:3). Nothing may occupy the vertical stack above or below the image region — no app bar, no bottom action row, no horizontal filmstrip, no caption row under a frame — because every 3dp of height costs 2dp of height on all three frames, while width up to the slack costs nothing at all. **That is the exchange rate, and it is why every piece of chrome on this screen is a column:** the sidebar, the readout block, the control block and the filmstrip all run top-to-bottom in the horizontal slack. The rule has no exceptions, and the filmstrip is not one: measured across the bottom of the window on 2026-08-08 it cost 38dp on every frame (675×450 → 618×412, ~16 % of the area) for an affordance the compare-and-cull loop does not use, so it was rotated into a 72dp vertical strip at the outer edge of the control flank, where it costs nothing (measured 2026-08-08: 675×450 with the strip both off and on). Instrumented tests assert the strip is *beside* a frame — sharing vertical extent with one, taller than it is wide, and overlapping neither a frame nor a control — and that toggling it does not move the frames.
    *   **Maximise:** Each frame carries a 44dp badge (and keys `1`/`2`/`3`) that fills the image region with that frame — 1211×908dp on the reference device, 4.1× the three-up area. `Esc` or a second activation returns to three-up. Maximise is transient view state and is deliberately **not** persisted.
    *   **Action Button Sizing and Labelling:** Move/Copy/Delete/Fullscreen/Previous/Next sit in a 2×3 grid of 80dp-tall controls to the right of the current frame, each as wide as the flank allows — ~158dp on the reference device, ~118dp with the filmstrip sharing the flank, against a 212dp floor for the block as a whole — positioned around — not overlapping — the images. **A control that changes a file is never icon-only:** each carries a permanent visible word and a permanent monospace key cap. Key hints must not be hover-revealed — the primary target is a tablet, which has no hover. Icon-only is permitted solely for view controls (readouts, filmstrip, value overlays, the coach-mark guide), none of which can lose a photograph.
    *   **Filing Verbs Are Derived, Never Euphemised:** The two filing controls are labelled `Copy` and `Move` from `SelectionActionLabels`, driven by the *Filing Action* setting; the configured verb is the emphasised primary and comes first, the other stays visible with its own shortcut. Labels such as "Keep", "Save" or "Favourite" are prohibited — they describe a feeling rather than what happens to the file, and under a move configuration they are false. Enforced by unit test. **The destination is a setting, not a constant:** every function in `SelectionActionLabels` takes the configured `selection_folder_name` (default `Selection`, blank falls back to it) and so does `FilingAction.phraseFor`, because a photographer who renamed the folder to `Picks` was being told about a folder that does not exist. The **button keeps the bare verb** so a long folder name cannot stretch or truncate the 190dp control; only the accessibility phrase, the context-menu row, the shortcut row and the snackbar name the folder.
    *   **No Overlapping Controls:** No two interactive controls may share screen bounds, and this is asserted by a UI test across the whole control block rather than checked by eye. On Previous and Next the maximise badge sits bottom-**left** specifically because the right edge belongs to the value overlay.
    *   **Sidebar:** One 88dp labelled sidebar on the left edge replaces both the Material `NavigationRail` and the selector's top app bar. 72dp items, 24dp glyph over an 11sp label — the label is mandatory. Item labels and their descriptions come from one `domain.guidance.SidebarAction` declaration that the guide also reads, so the legend cannot call a control something the control does not call itself. Two zones separated by a rule: session actions (Folder, Scan, Bursts, Legend, overflow) above, app destinations (Cull, Stats, Dupes, Setup) below. Toggles and destinations share one active treatment, because "this screen is open" and "this option is on" are the same statement. **Scanning variant:** the Scan item is replaced in place by a `412 / 842` counter over a red **Cancel** action. A scan must never take the screen — culling continues while it runs. **Queued variant:** a scan asked for while Group Similar Series is running, or a grouping change made during a scan, takes the same treatment with `Queued` in place of the counter. Neither control is ever *disabled* — a control that does nothing when tapped reads as a frozen app — and both queued states carry the same Cancel. The pair is implemented symmetrically through one pure state machine (`domain/session/SelectorWorkQueue`): if A-during-B queues, B-during-A queues too, and a unit test asserts each rule in both directions.
    *   **Equal Frame Sizing (non-negotiable):** All three frames are identical in size. The current frame is marked **only** by being centred and by a 2dp Indigo-500 border; neighbours must never be dimmed, scrimmed, shrunk or blurred — a dimmed or smaller neighbour cannot be judged for exposure or sharpness, which is the task. Tiles are the image: the solver resolves the active image aspect ratio (3:2, 4:3, or reciprocal for portrait) from whichever constraint binds, and portrait frames mid-burst are pillarboxed into the footprint so they cannot reflow the grid.
    *   **A Flank Is Always Reserved, Because It Holds the Way Back:** `FrameGeometry.threeUpLayout` never returns a `flankWidth` below `MinimumControlBlockWidth` (212dp), whatever the view toggles say. The control block is not optional chrome: the details and filmstrip toggles live inside it, and no key is bound to them, so a flank of 0dp is a one-way door — switching the readouts off took away the control that switches them back on. It also un-centres the screen, because the current frame is centred *by arithmetic* (`flank | frame | flank` consuming the region exactly) rather than by an `Alignment`, so two zero-width flanks left the row's default `Arrangement.Start` to draw it hard against the left edge while the neighbour row below stayed centred. Row 1 additionally centres explicitly in both the layout and the coach overlay, so the few dp the solver can round over are split rather than paid entirely on one side. Unit tests assert the floor holds for every combination of the toggles and that the row never overflows the region; an instrumented test asserts the frame stays centred with the readouts hidden.
    *   **Value Readouts — Every Number Touches Its Frame:** Placement, not tabulation, establishes which frame a value belongs to. **Current frame:** a 388dp block to its left carrying filename, one-line EXIF, a rule, then one `icon · full name · value` row per metric with the 2dp goodness bar beneath — this block is also the legend that teaches the glyphs. **Previous and Next:** a 148dp column carrying filename, a two-line exposure block (`1/250s · f/2.8` / `35mm · ISO 400`, tabular mono so the two frames' values align vertically; lens omitted), a rule, then `icon · value · bar` rows in the same order. Metric order comes from the `ScoreMetric` enum so the three frames cannot disagree about it. Neighbour values render **outside** the frame where ≥156dp of free width exists and **overlaid on its right edge** otherwise — one measurement, both branches tested. Overlays are suppressed while a frame is maximised and can be toggled off entirely (`overlay_values_visible`, default on). Readout visibility is persisted (`details_visible`).
    *   **Filmstrip — Vertical, and Off by Default:** A 72dp-wide **vertical** strip with a 1dp left border, scrolling top-to-bottom down the outer (right) edge of the control flank — **never a horizontal bar across the bottom of the window** (see *Chrome Placement*; the bottom arrangement is priced at 38dp per frame and is prohibited). The width is a measurement, not a taste: at 3:2 on the reference device each flank has 82.5dp of slack above the 260dp the control block needs, so 72dp plus the 8dp gap is free and anything above 74.5dp starts taking height off all three frames. A unit test asserts the frames do not move when the strip is toggled. `FrameGeometry.threeUpLayout` returns the strip's width as part of the solved layout, so the coach-mark overlay reserves the same column; where a window is too narrow to hold the strip beside the view toggles the strip is dropped rather than drawn over them, and with the readouts hidden the flank still keeps room for both. 60dp-wide thumbnails (40dp tall landscape / 80dp portrait — width is the constant, because in a column a ragged cross axis cannot be scanned; 3dp radius, 1dp outline, .85 opacity; the current thumbnail is 2dp Indigo-500 at full opacity). Each thumbnail carries a single 6dp sharpness dot tinted by goodness and no text. With Group Similar Series on, thumbnails in the current burst carry a 2dp Indigo-600 marker down their leading edge and each new burst starts after a 10dp gap. A mono caption **below** the list reports the visible range (`115–156 of 842`), placed below rather than over it because at this width an overlaid caption would cover a thumbnail outright. Hidden while a frame is maximised. **Visibility is persisted (DataStore `filmstrip_visible`) and defaults to off:** the compare-and-cull loop is Prev/Next and the two neighbour frames, so the screen opens on three photographs and nothing else; the strip is random access to the rest of the shoot and is one tap away in the view cluster. The default is pinned by a unit test on `SettingsRepository.DEFAULT_FILMSTRIP_VISIBLE`, because every instrumented test sets the preference before asserting and none of them would notice it drifting.
    *   **No App Bar:** The selector has no top app bar. Folder name and the burst chip move into the head of the readout block; `127 / 842` closes the control block. A 44dp bar costs 29dp of height on all three frames, which is a price this screen does not pay for chrome.
    *   **The Position Readout States Whether the Total Is Final:** Discovery streams, so for the first seconds of a large shoot the total is a *running* total. The readout is therefore `127 / 842+` while enumeration is still producing photographs and `127 / 842` once it has settled, from one pure formatter (`SelectorLabels.position`); the accessibility description says "so far, still loading" in the same state. Printing the running total bare would state a folder size nobody has counted. Nothing else in the layout changes while loading — no spinner, no blocked controls: the first batch of 24 is enough to start culling and the photographer does so while the rest arrives.
    *   **First-Run Navigation Hint:** Because the layout draws no arrows over photographs, a single centred pill ("Tap either side to browse" + "Got it") is shown once, 16dp above the bottom of the image region, to teach that the neighbour tiles navigate. It is the **only** permitted *image-adjacent* overlay in the selector — that is, the only element **whose purpose is to teach** may occupy space over or inside a frame's bounds. The neighbour value overlays (§ *Value Readouts*, where the flank is under 156dp) and the 44dp maximise badge (§ *Maximise*) also sit inside a frame and are **not** exceptions to this rule: they are chrome the user reads while judging a photograph, they are permanent and toggleable rather than one-shot, and they are governed by their own clauses. The distinction is purpose, not pixels — guidance is rationed inside a frame because it earns its place once and then never again. The seen flag is persisted (`hasSeenNavHint`) and the hint never returns. This restriction governs **placement**, not the existence of guidance: a user-invoked or action-triggered, transient, self-dismissing teaching surface is a different category from chrome, and the two below are permitted precisely because neither ever occupies a frame's bounds — both are laid out inside the horizontal slack, and a UI test asserts their bounds do not intersect any of the three frames.
*   **Coach-Mark Guide (replaces the shortcut sheet):** `?`, the keyboard glyph in the control block and the overflow menu open a full-window coach-mark overlay, which is also shown once at first launch. It dims the screen with a Zinc-950 scrim at 72 % — the real chrome stays visible beneath it, because the overlay's job is to label *that*, not a diagram of it — and reserves the real geometry (88dp sidebar column, both flanks, all three frame footprints) through the same `FrameGeometry.threeUpLayout` solver, with the same `detailsVisible` and `filmstripVisible` inputs, the layout itself calls, so every callout lands in the slack and **no callout may cover a frame**. **It is also the legend**: the sidebar callouts name every item in the rail from `SidebarAction` and `Screen.all`, and the readout callout carries one row per `ScoreMetric` — its real glyph, its display name, and which direction is better — so the icons are explained beside themselves rather than in a sheet that covers them. The 88dp sidebar column is reserved and left **empty** for exactly that reason, and the left flank spaces its three blocks apart (`Arrangement.SpaceBetween`) so each lands level with what it explains: session actions at the top of the screen, the readout in the middle, destinations at the bottom. An instrumented test asserts the callouts never overlap one another as well as never covering a frame. One callout per region: sidebar session actions, sidebar destinations, the readout block, the three frames, the control block, the keys that drive no on-screen control (`1`/`2`/`3`, `Esc`, `?`), and the filmstrip — whose callout sits at the foot of the control flank, immediately left of the vertical strip it labels, with the strip's own column reserved and left empty. **It must fit on one screen and must not scroll** — a guide that scrolls is documenting rather than teaching. Every row is generated from `SelectorGestures` (`SelectorShortcut` and `FrameGesture`), never written as a literal; unit tests assert the advertised set equals the bound set exactly, that no advertised gesture is destructive, and that no callout names a glyph. Callouts for chrome the user has switched off (readouts, filmstrip) are omitted. `Esc`, a tap on the scrim or **Got it** closes it; shortcuts stay suppressed while it is open, except `Esc`. The scrolling `input → effect` sheet it replaces is removed: a list of labels is the weakest possible way to explain a control the user can already see, and every control here already carries a permanent word and key cap.
*   **One-Time Action Explanations:** One-shot explanations are identified by `com.photoselectortoolbox.domain.guidance.SelectorHint` (`filing_action`, `delete_undo`, `maximise_frame`, `scan_scores`, `selector_tour`) and their dismissals persist as one DataStore string set (`seen_first_run_hints`), so adding a hint adds no preference key. The enum carries **keys only** — the wording is derived at render time by `SelectorHintText` from the user's *current* settings (`SelectionActionLabels`/`FilingAction`, the Selection folder name, File Sorting, and `DeferredDeletion.UNDO_WINDOW_MILLIS`) so a hint names the configured verb, folder and window; `SelectorHint.FILING.namesFilingVerb` marks the hint that cannot be written as a constant. Labels such as "Keep", "Save" or "Favourite" are prohibited here as they are on the controls, and a unit test asserts the euphemisms never appear. **Only three are raised as cards**, and only where the *effect is invisible*: the first filing (the photograph left the frame and nothing says where it went — the important one), the first delete (that it is deferred and revertable for 30 seconds), and the first maximise (that `Esc` or a second press returns to three-up). `scan_scores` is defined and worded but deliberately never raised, because the bars and the Legend item appear on screen at the same moment; `selector_tour` is the guide, not a card. Each card fires exactly once, auto-dismisses after 9 seconds, is suppressed while the guide is open, and is placed in the flank beneath the readout block — never over a frame and never adding height above or below the image region. Where no flank is wide enough (readouts hidden, or under 240dp) the card is not drawn **and the hint is not marked seen**, so it survives to a window that has room. Unknown stored keys are ignored rather than treated as seen. A **Reset guidance** entry in Settings clears the set together with `hasSeenNavHint` and `seen_fullscreen_gesture_hint`; a reset that leaves two hints permanently dismissed is not a reset.
    *   **Context Menu:** Long-press or right-click on any frame opens a 230dp menu at the pointer with Move to «folder» `M`, Copy to «folder» `C` (the configured `selection_folder_name`, from `ActionLabel.phrase`), Delete `Del` (destructive colouring), Photo details, and Open fullscreen `F`; 44dp rows with mono key hints.
    *   **Action Feedback:** Actions confirm through a centred snackbar 96dp above the bottom edge (min 340dp, 1dp outline, 10dp radius) carrying the message and a 2dp Indigo countdown line that drains over 30 seconds. Messages: "Moved to «folder»", "Copied to «folder»", "1 image deleted", "Scan complete · N images analysed" — where «folder» is the configured `selection_folder_name`, generated by `SelectionActionLabels.confirmation(action, folderName)` and never written as a literal, so the snackbar and the filing hint card that fire together name the same folder. The message and its `onUndo` are one fact about one operation and are therefore decided together in the ViewModel, not held in the composable's `remember` — a message owned by the composable can outlive, or disagree with, the operation it claims to describe. The countdown is driven from wall-clock time, not from a frame-clock animation, so it agrees with the wall-clock timer that commits the deletion.
    *   **Undo Is Offered Only Where It Works:** The 30-second window is `DeferredDeletion.UNDO_WINDOW_MILLIS` — one constant shared by the countdown line and the timer that commits the deletion, because two copies of it is a countdown that lies. `onUndo` is non-null only for operations `com.photoselectortoolbox.domain.curation.UndoPolicy` declares reversible: a **deferred delete** (removed from the list at once, committed to disk when the window closes, another action arrives, or the screen is left — so reverting is a list insertion and cannot fail), a **committed delete** where `canTrash` is true (restored from the backend's trash), and a **move** whose `FileOperationResult` carried a destination URI. **Copy is deliberately not undoable** — the original was never touched, so the only thing an undo could do is delete the file the user just asked for. An UNDO that silently does nothing is worse than none.
    *   **Optimistic Actions Own Their Rollback:** Move and Delete are applied to the list *before* the file system confirms, with the transfer running on the `@ApplicationScope` application-lifetime scope so it survives the ViewModel being cleared. On failure the frames return to their recorded slots, re-inserted in ascending index order, and `currentIndex` is re-derived from the **URI** of the frame on screen rather than from a stored integer. A failed **copy** rewinds nothing, because the source file never left. All of it is pure logic in `domain/curation/` with JVM unit tests.
    *   **Motion:** 150–200ms standard easing; score bar widths animate over 180ms. Image transitions **crossfade only** — never slide, scale or parallax. The user is judging sharpness, and movement lies.
*   **Samsung DeX:** Treat as Expanded window size class. Support resizable windows. Enable hardware keyboard shortcuts in both standard and fullscreen modes: `←`/`→` previous/next · `M` move · `C` copy · `Del`/`Backspace` delete · `F` fullscreen · `1`/`2`/`3` maximise previous/current/next · `?` coach-mark guide · `Esc` leave fullscreen or maximised / close sheet / close menu / close the guide. **Shortcuts are suppressed while any sheet, dialog or the guide is open, with the sole exception of `Esc`** — a stray `M` while configuring a scan must not move the frame behind the sheet. Key hints are **permanent** mono key caps on the controls themselves, never hover-revealed. The `?` guide and every hint card are generated from `SelectorGestures`, the same object that defines the bindings, so an advertised shortcut cannot outlive the binding it describes.
*   **Edge-to-Edge:** All screens must use `enableEdgeToEdge()` and properly handle `WindowInsets` for system bar padding. **On the selector the handling is deliberately horizontal-only**, and the reasoning is the same arithmetic as everything else on this screen: measured on the reference device the system bars are 36dp top and 32dp bottom, and padding for them would take 34dp off all three frames and put the reference frame at 416dp — below the documented floor. Width is surplus, so the selector pads for `safeDrawing` on the horizontal sides (where a display cutout or a rotated navigation bar actually clips content) and draws through the vertical bars, which `enableEdgeToEdge()` renders transparent. The cost is stated rather than hidden: the bars overlay the outer 28dp of the top frame and 24dp of the bottom row, and a photographer who wants an unobstructed look has maximise (`1`/`2`/`3`) and fullscreen (`F`), both of which already hide the system bars outright. Every other screen pads for all insets as normal.
*   **DeX Metadata & Layout Limits:** The manifest must include `com.samsung.android.keepalive.density` metadata and `resizeableActivity="true"`. To optimize desktop window launching (e.g. on 10-inch Chromebooks or DeX), explicit layout size limits (default width 1024dp, default height 768dp, min width 800dp, min height 600dp) are configured.

## 3. Feature Set & Exclusions

The Android app includes all desktop features except:
*   **Excluded:** Local AI Aesthetic Evaluation via **Ollama VLM** — battery drain and insufficient compute on mobile. (The Android Desktop app instead offers a lightweight on-device **TFLite NIMA** aesthetic score — see below.)
*   **Android Desktop — On-Device Aesthetic Score:** An opt-in ("AI Aesthetic Score (beta)" in the scan configuration) on-device aesthetic score computed by a small NIMA (MobileNet) model via TensorFlow Lite, normalized to a 1.0–10.0 scale and cached in Room (schema v2 `aestheticScore` column). It is gated behind the cheap OpenCV sharpness metric (only sharp images are scored) to protect battery, and degrades gracefully (no score shown) when no model asset is bundled. Surfaced as an "Aesthetic" `ScoreChip` in the comparison layouts and the fullscreen viewer. **PhotoTok / PhotoTok remains fully excluded** from aesthetic scoring to keep the phone client lightweight.
*   **Excluded:** CLI interface — not applicable on Android.
*   **Excluded:** Homebrew distribution — uses APK/Play Store instead.
*   **Excluded:** ExifTool bundling — replaced by AndroidX ExifInterface.
*   **Excluded:** SMB path resolution — Android handles network shares via SAF providers.

## 4. Touch, Pointer & Keyboard Interaction

*   **One Gesture Vocabulary, Enforced:** Horizontal swipe means *previous / next* in every layout and every viewer in this product. **No destructive or filing action may be bound to a bare gesture, anywhere.** `FullscreenGesture.destructive` exists so this rule is data a unit test asserts rather than a sentence in a design document; the compact layout's swipe-left-to-delete and the fullscreen viewer's swipe-left-to-delete are both removed. Double-tap is reserved and files nothing.
*   **Photo Navigation:**
    - **Tablet / Large Screens:** Tap a neighbour frame, use the labelled Previous/Next controls, swipe the image region horizontally, or press `←`/`→`.
*   **Fullscreen Viewer / Image Zoom:**
    - **Tablet / Desktop Fullscreen:** Pinch-to-zoom, double-tap to toggle fit ↔ **true 100 %** (one image pixel per device pixel, computed from the frame's own dimensions — not a fixed magnification advertised as "100%"), vertical drag down to dismiss, **horizontal** swipe to navigate via `HorizontalPager`. Vertical drag is ignored while zoomed, where it is a pan.
*   **Minimum Touch Target:** 48dp for all interactive elements.
*   **Score Badge Legibility (Android Desktop):** Post-scan quality badges must not be bare icon-and-number pairs. Every metric is defined once in `com.photoselectortoolbox.domain.scoring.ScoreMetric` (short chip label, display name, plain-language description, **its glyph**, value format, whether higher or lower is better, and its normalisation range). The glyph is load-bearing rather than decorative: on Previous and Next it is the only thing identifying which metric a number belongs to, so it is declared on the enum and resolved to a vector by an exhaustive `when`, and a unit test asserts the glyphs are distinct and the mapping total and rendered via the shared `ScoreChip`/`ScoreChipRow` components. Chips show icon + short label + formatted value; the label may be dropped only where space is genuinely unavailable (thumbnail overlays, fullscreen), in which case the accessibility description still carries the full name, value and direction. Value formatting must be `Locale.US` so decimal separators do not vary by device locale. There is exactly **one** glyph mapping (`ScoreMetricIcon.vector`), shared by the chips, the readouts and the guide; a second mapping is what let the legend teach a spotlight for highlight clipping while the frames drew a sun. The **Legend** sidebar item is always present — it names every icon on the screen, the sidebar included, so it is most useful before anything has been scanned — and opens the coach-mark guide rather than a sheet.
*   **Score Direction Bar & Best-of-Three (Android Desktop):** Every chip renders a **2dp direction bar** beneath its value. `ScoreMetric.goodness(value)` normalises the raw value onto 0..1 where 1 is always good regardless of which way the underlying number runs (sharpness 5–100 higher-better; noise 0.2–7, highlight 0–10, shadow 0–14 lower-better; aesthetic 1–10 higher-better). Bar length is `6% + goodness × 94%` on a Zinc-700 track and is tinted `#34D399 ≥ .62 / #FBBF24 ≥ .33 / #F87171` — so three frames are comparable across metrics on wildly different scales without reading digits. The frame holding the best value for a metric **among the frames currently visible** gets a 5dp Indigo dot after its value; `bestIndexOf` returns null when fewer than two frames carry a value ("best of one" is not information) and resolves ties to the earliest frame so the marker cannot flicker. The accessibility label states the name, the value, the direction, and "best of the three visible frames" where applicable. A frame with no scores shows one dashed "Not scanned" ghost chip rather than an empty row.
*   **Context Menus:** Long-press activated. No hover-dependent interactions.
*   **Desktop/Input Enhancements**: Mouse pointer cursors automatically display hand pointer shapes (`PointerIcon.Hand`) when hovering over interactive components (buttons, clickable images, list thumbnails). Folder drag-and-drop capability is supported, enabling users to drag a photo folder from external file managers directly into the app window to load it automatically.

## 5. Image Analysis (Algorithm Parity)

All analysis algorithms must produce equivalent results to the desktop Python implementation:
*   **Sharpness:** Center 50% crop → 8×8 grid → max Laplacian variance (OpenCV Android: `Imgproc.Laplacian` with `CV_64F`).
*   **Noise:** MAD of Laplacian filter: σ = median(|∇²I - median(∇²I)|) / 0.6745.
*   **Highlight Clipping:** Percentage of grayscale pixels ≥ 254.
*   **Shadow Clipping:** Percentage of grayscale pixels ≤ 2.
*   **Duplicate Detection:** SHA-256 file content hashing via streaming `DigestInputStream`.
*   **Image Grouping:** Three levels matching desktop: Time & Filename, Time + Fast Similarity (8×8 dHash, Hamming ≤ 10), Detailed Similarity (16×16 dHash, Hamming ≤ 24).

## 6. Persistent Cache (Room)

*   **Room Database:** SQLite cache at app-internal storage storing sharpness, noise, highlight/shadow clipping scores.
*   **MRU Limit:** 10,000 entries, pruned by last access time (matching desktop).
*   **Cache-First Loading:** On folder open, restore cached values immediately from Room DB. Scores are pre-populated into `ImageItem.scanResult` on discovery, validated against file size and modification time. Manual scans skip already-cached entries.
*   **Clear Cache:** Available in Settings screen with confirmation dialog.

## 7. Performance & Battery

*   **Thread Pool:** `minOf(4, availableProcessors)` — reduced from desktop's `min(8, cpuCount + 4)` for battery conservation. Both the default value and the settings UI slider enforce a maximum of 4.
*   **Parallel Image Scanning:** Multiple images are analyzed concurrently using a `Semaphore`-gated coroutine pool (sized by the thread count setting). Within each image, sharpness, noise, and clipping analysis run in parallel via `async`/`await`. Clipping analysis (highlight + shadow) uses a combined single-pass method to avoid duplicate bitmap→Mat and grayscale conversions.
*   **Progressive Folder Discovery:** A SAF tree is walked **iteratively, breadth-first**, with one `ContentResolver.query` per directory against `DocumentsContract.buildChildDocumentsUriUsingTree` projecting `COLUMN_DOCUMENT_ID`/`DISPLAY_NAME`/`MIME_TYPE`/`SIZE`/`LAST_MODIFIED` together; child URIs come from `buildDocumentUriUsingTree`. `DocumentFile.listFiles()` plus per-attribute getters is prohibited here — it costs roughly five binder round-trips per photograph. Discovery emits **cumulatively and progressively**: a first batch of 24 (enough to start culling: the current frame, its neighbours and some filmstrip either side), then batches of 250, then a final complete snapshot. Each batch is sorted by filename **within the batch** and appended; the visible list is never re-sorted, because re-sorting moves photographs out from under a photographer mid-cull. Consumers must merge append-only, and a consumer that needs the whole folder (duplicates, statistics) calls `ImageRepository.discoverAllImages(uri)` rather than `discoverImages(uri).first()`, which would now see only the first batch. The selector merges through the pure `domain/session/ProgressiveMerge`, de-duplicating against **every URI ever published for the folder** — not against what is currently on screen, or a photograph the photographer has already filed away would be resurrected by the next cumulative emission. `currentIndex` is set to 0 only on the first batch of a new folder; grouping and the cached-score restore run off the settled list (debounced), never per batch, because both rebuild what the photographer is looking at. Selecting a new folder cancels the previous discovery and dimension jobs and clears the published set in one place — a surviving set makes the new folder look empty with no error anywhere. The walk is guarded by `coroutineContext.ensureActive()`, and a directory that cannot be listed is logged and skipped rather than aborting the folder open. `Selection`/`Selected` sub-folders are skipped case-insensitively.
*   **A Background Pass Merges the Field It Computed, Never the Item:** Score restoration from the Room cache and the scan itself both work from a snapshot of the image list — one across an IO read per photograph, the other across minutes — while EXIF and dimensions are written into the same items by other coroutines. Both therefore fold their results back through `domain.session.ScoreMerge`, which writes `scanResult` alone; `ScoreMerge.scoresOf` takes the scores out of a snapshot so passing whole items forward is not expressible. Merging the items reverts everything that landed meanwhile: because EXIF is only re-fetched on navigation, and because in an unscanned folder *every* item lacks a score, the frame the photographer was looking at simply showed no EXIF until they moved away and back. `ScoreMerge` is pure and unit-tested without a dispatcher — the only route to the old code was a `withContext(Dispatchers.IO)` hop that escapes virtual time, which is why no test ever covered it.
*   **Dimensions Are Resolved Off the Enumeration Path:** Folder enumeration must not read image content. `ImageRepository.resolveDimensions(uris)` returns header-only sizes as `ImageDimensions`, driven by the caller for the visible range first and backfilled in the background on `Dispatchers.IO`; each URI is read at most once per process, including negative results. `ImageDimensions.UNKNOWN` (`aspectRatio == null`) is a normal, safe state — the frame solver uses its 3:2 default until the true ratio arrives, and a missing dimension never blocks a frame from being drawn. The selector drives it in two passes: the visible range (current ± 1 plus the filmstrip's neighbourhood) is resolved on every navigation, and the rest is backfilled nearest-frame-first in a pass that is **not** cancelled and restarted per navigation — restarting would discard in-flight work and re-read headers already read. Results are applied to state in batches of 24, because a per-image update in an 842-frame folder is 842 recompositions of the whole selector.
*   **Neighbour Prefetch:** The frames just beyond the visible three (current ± 2 and ± 3, nearest-first and forward-biased) are decoded ahead of the photographer through the application's tuned Coil `ImageLoader` — the Android form of the desktop's `preload_next_candidates`. Requests are sized to a frame (1440 × 1080 px) rather than to the original, and prefetches that fall outside the window on a fast scrub are disposed while ones still inside it are left alone. The window is deliberately narrow: every prefetched frame competes for the same memory cache and decode threads as the three on screen, and a prefetch that slows the visible decode has made things worse. Prefetch is an optimisation and never a requirement — any failure to warm a frame leaves the visible decode exactly as it was.
*   **Image Decoding:** Use `BitmapFactory.Options.inSampleSize` or `ImageDecoder` for memory-efficient downsampled decode. Hardware bitmaps for display, software bitmaps for analysis. Forced decoding in `ARGB_8888` for analysis to avoid pixel quantization that truncates bright highlights and dark shadows.
*   **Battery Awareness (Deferred):** Reduce worker threads when battery < 20%. Pause scan and notify when battery < 10%. Use `WorkManager` with `Constraints.Builder().setRequiresBatteryNotLow(true)` for background scans. *Status: WorkManager dependency is declared but feature is not yet implemented.*
*   **Memory Management:** Coil handles display image caching, explicitly configured rather than left at defaults: memory cache at **30 % of available app memory** (three visible frames at up to 675×450dp are ~4.9 MB each on a 2× tablet, a maximised frame at 1211×908dp is ~17.6 MB, and neighbour prefetch keeps several more warm — while leaving headroom for the analysis bitmaps), a **512 MB** disk cache under `cacheDir/image_cache` (holding Coil's *decoded, downsampled* frames — re-reading and re-downsampling a 45 MP RAW costs far more than reading back the 1350x900 result, and a culling session scrubs the same frames repeatedly), and `respectCacheHeaders(false)` because source images are immutable. Analysis images decoded at max 2048px on longest edge using `ImageDecoder` on API >= 28 (supporting RAW formats) and `BitmapFactory` on older APIs. SHA-256 uses streaming reads. Mat objects released immediately after use. EXIF data cache uses bounded LRU eviction (max 50 entries). dHash values are cached per grouping pass to avoid redundant bitmap decoding.
