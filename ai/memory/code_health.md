# Code Health Backlog & Lessons

Refactoring candidates and structural lessons. Owned by `@shared-code-health-agent`; any agent may append. Format for backlog items:

```markdown
## [OPEN|DONE] YYYY-MM-DD - Short title
**Where:** file paths / modules
**Debt:** what is wrong and why it matters
**Proposal:** the safe refactoring, referencing `ai/skills/refactoring-guide/SKILL.md` patterns
```

Lessons use the standard `ai/memory/` format (Learning/Action).

## 2026-08-08 - A Coordinator's Unmeasured Number Becomes Everyone Else's Established Fact
**Learning:** Three times in one session a coordinating agent emitted a figure that *sounded* measured and was not, and each travelled further than the same error from a subagent would have. A "~146 dp height leak" was reasoned backwards from arithmetic against the window height, then written into `code_health.md` as a finding and into two agent briefs as an established diagnosis — in the same briefs that instructed the agent to measure rather than guess. There was no leak: the coordinator's model shared the failing test's assumption about which constraint binds, so it reproduced the same artefact, and the agreement between model and test was read as corroboration when it was one observation counted twice. Separately in the same session an emulator was left in the wrong rotation and the resulting "7 % frame" was reported as a finding, and a baseline-counting regex under-reported the pre-existing failures. The delegating agent's output does not arrive as advice; it arrives as a premise. It gets copied into briefs, backlog items and `ai/memory/`, where it outlives the session, and disproving it costs the subagent a full verification pass — here the agent's first act was to measure, which took minutes and voided the brief it had been given.
**Action:** Every quantity that leaves a coordinator carries its provenance: **measured** (name the command and the device it came from), **computed** (state the inputs and the model, and label it a prediction to be checked), or **assumed**. Only measured numbers may be written into `ai/memory/`, into a `[OPEN]` backlog item, or into a brief's findings; a computed number goes in as the hypothesis it is — and where the measurement is cheap and the subagent has the device, brief the *question* ("measure the frames at reference geometry and tell me which constraint binds") instead of the answer, because a wrong answer costs more than no answer. Treat your own model agreeing with a failing test as one data point, not two: name the assumption they share before calling it confirmed. When a number does turn out wrong, chase every place it was copied to — the brief, the backlog entry, the requirements line — the retraction does not propagate on its own.

## 2026-08-08 - A Merge That Replaces the Whole Item Is a Rollback, and a Dispatcher Hop Is Where It Hides
**Learning:** `restoreCachedScores` snapshotted the image list, spent one Room read per photograph on `Dispatchers.IO`, then folded the **pre-IO snapshot** back over live state: `if (image.scanResult != null) image else byUri[image.uri] ?: image`. It reads as a merge and is a rollback — every image without a score is replaced by its stale copy, which in an unscanned folder is all of them, so the EXIF another coroutine wrote during the IO window was discarded. EXIF is only re-fetched on navigation, so the frame the photographer was looking at simply stayed blank. `runScan` had the same snapshot-mutate-write-back shape. Two things kept it invisible: the only route to the code was a `withContext(Dispatchers.IO)` hop, which escapes `runTest`'s virtual time, so every attempt to assert it through the ViewModel was a race rather than a test — the tell is that adding `advanceUntilIdle()` changes nothing, because the work is not on the test scheduler at all; and the fakes pre-populated `exifData`, so the production *arrival order* — EXIF landing after the snapshot was taken — was never exercised.
**Action:** Merge the field you computed, never the item you computed it from. Express it as a pure function over `(items, computedValues)` that has no way to say "take the whole old item" — `domain/session/ScoreMerge.apply` is the worked example, and `ScoreMerge.scoresOf` exists so a caller cannot hand items where a field map is wanted. Anything captured before a suspend point is input, never output: on the way back, re-read current state and write only the field. Logic reachable only through a dispatcher hop does not get tested, so extract it pure *before* writing the test rather than after failing to — if a test needs `advanceUntilIdle` to settle a data question, and still fails, the data question is in the wrong layer. And build fakes that reproduce the production arrival order, not just its end state: a fixture that supplies up front what production computes later erases the exact window every merge bug lives in.

## 2026-08-08 - A Test Fixture That Routes Around Production Code Becomes a Production Feature
**Learning:** Both `:android-desktop` suites — about 50 call sites — opened `gdrive://` folders on purpose, documented at `SelectorViewModelTest.kt:51` as the way to skip SAF's `DocumentFile` permission dance. That quietly made the Google Drive source load-bearing for the tests, even though it was redundant as a feature (SAF already mounts Drive as a document provider): deleting its branch dropped every one of those call sites into `DocumentFile.fromTreeUri` at once, and the resulting failures present as layout and timing bugs, nowhere near the code that was removed. The tests reached for a second URI scheme because the interface offered no seam — the ViewModel called `takePersistableUriPermission` and `DocumentFile` itself, and a `DocumentFile` cannot be faked at all.
**Action:** When a test takes a documented shortcut past production code, read it as a missing seam in the production interface rather than as test convenience; the shortcut will be inherited by the next fifty tests and will hold the bypassed code in place. Put the capability the test actually needs on the interface — `ImageRepository.openFolder(context, uri): String?` persists the grant and confirms the folder resolves, so nothing above the repository touches SAF — and let the fake satisfy the interface instead of an alternate code path. No caller above a storage interface may branch on a URI scheme. Before deleting any feature, grep two places the diff will not show you: the **test sources**, where the migration cost actually lives (seam first, deletion second — that is two changes and should be two), and the **persisted keys**, for values only that feature could have written. A retired `gdrive://` URI left in DataStore greets a returning photographer with "permission revoked or directory deleted" for a folder they never lost, so the read must drop it (`SettingsRepository.lastFolderUri`) rather than the writer merely stopping.

## 2026-08-08 - A Cross-Cutting Duty That Lives Only in a Role Description Does Not Happen
**Learning:** Two mechanisms existed to carry an improvement from one product to its siblings, and neither closed the loop. `ai/memory/bolt.md` (2026-07-31) recorded the SAF-enumeration anti-pattern as a general rule from PhotoTok, and Android Desktop still contained that exact anti-pattern — plus a per-file `openInputStream` the lesson did not cover — more than a week later; `ai/memory/palette.md` the same day prescribed coach marks over label lists, and Android Desktop kept the label list. `docs/shared/FEATURE_PARITY.md` tracks only Desktop→Android *features* and has no row for interaction or performance patterns, and the obligation to evaluate parity sat in `ai/ROUTING.md` as a coordinator duty — a sentence in a role description rather than a step in the checklist that actually runs at the end of every task. Writing a lesson down is a diagnosis, not a distribution mechanism: agents read `ai/memory/` for the product they are already working in, so a lesson learned in one product has no route into another. The user, not the framework, eventually noticed.
**Action:** Put every cross-cutting obligation in the checklist that executes, never only in the role that owns it — an unchecked duty is decoration. When a fix or lesson lands, name the sibling products it could apply to and record the decision, *including* "not applicable, because…", in the shared ledger where the next agent will look, not in the task summary that disappears with the session. And when the same lesson appears in `ai/memory/` twice from two products within days, read it as proof the propagation step is missing rather than as two lessons.

## [DONE] 2026-08-08 - The instrumented suite is red at HEAD, so nobody can tell a regression from the status quo
**Landed 2026-08-08:** both halves. `NavigationTest` now clicks `nav_<route>` test tags instead of reaching for the retired `NavigationRail`'s semantics, and the frame-height assertion is expressed as a *function of the measured window* — it re-derives the expected frame through `FrameGeometry.imageRegion` + `threeUpLayout` and applies the absolute 440dp floor only where the window is at least `FrameGeometry.ReferenceWindowHeight` (900dp), so a 1280×800 CI emulator reports "smaller than the product targets" by staying silent rather than by failing. The fixed 45 % threshold is gone: it was reporting the display's own ceiling as a defect, because at 1480×924 a 16:9 frame is width-bound at 684×385 and 385/924 is 41 % on any ~1.6:1 window. Verified green: 36/36 on a `medium_tablet` AVD resized to the reference 2960×1848 @ 320dpi.
**Where:** `products/android/android-desktop/tests/instrumented/com/photoselectortoolbox/ui/NavigationTest.kt`, `SelectorScreenTest.kt` (`threeUpLayout_framesUseTheHeightTheDisplayAllows`)
**Debt:** `:android-desktop:connectedDebugAndroidTest` fails **5 of 27 tests on unmodified `HEAD` (180ec23)**, verified by running it in a clean worktree on a `medium_tablet` AVD (1280×800dp, natural landscape). Four are `NavigationTest` (`navigateBackToSelector`, `navigateToDuplicates`, `navigateToStatistics`, `navigateToSettings`), all `Failed to inject touch input … could not find any node that satisfies ((OnClick is defined) && hasAnyDescendantThat(ContentDescription = 'Duplicates'/…))` — the sidebar rewrite replaced the `NavigationRail` these tests reach for, and they were never updated. The fifth is `threeUpLayout_framesUseTheHeightTheDisplayAllows`: the frame is **328.5dp of an 800dp window (41 %)** against a `≥45 %` assertion. That threshold comes from `REQUIREMENTS.md` § 2 and was calibrated on the 1480×924dp reference device; the 88dp sidebar and 76dp filmstrip are fixed sizes, so they take proportionally more of a smaller window and the ratio falls below the floor without anything being wrong. This is the more expensive half of the debt: a suite that is always red trains everyone to ignore it, and it is exactly the gate `ai/memory/code_health.md` (2026-07-27) says an agent cannot evaluate before pushing. The 2026-08-08 UX overhaul added 7 instrumented tests that all pass and changed none of these 5 — but establishing that took a full baseline run in a second worktree, which is the tax this debt charges on every future branch.
**Proposal:** Two separate fixes. (1) Update `NavigationTest` to the sidebar's actual semantics — the sidebar items carry test tags already, so match `hasTestTag` rather than a `ContentDescription` on an ancestor with `OnClick`. (2) Decide whether the 45 % floor is a property of the *design* or of the *reference device*: either express it as a function of window height (with a lower floor for windows under ~900dp) or assert it only on a window at least as large as the reference. Do not simply lower the constant — the floor exists because "the images look small" is not something a suite notices on its own (`ai/memory/palette.md` 2026-08-07). Until both land, treat a red instrumented run as uninformative and diff it against a baseline worktree.

## [OPEN] 2026-08-08 - Tablet portrait is specified to move chrome below the frames and does not
**Where:** `docs/products/android-desktop/DESIGN.md` §15.1, `products/android/android-desktop/src/com/photoselectortoolbox/ui/selector/ThreeUpSelectorLayout.kt`
**Debt:** §15.1 says that in tablet portrait — still Medium, still this layout — the readouts and controls move *below* the frames and the filmstrip returns to a horizontal row, because in portrait height is the surplus axis and the flanks are what has run out. None of that is implemented: the layout is the same landscape arrangement at every size, and the only portrait-aware behaviour is that the frame solver caps each flank at a quarter of the region and drops the filmstrip when the flank cannot hold it beside the view toggles. That is the safe half — nothing overlaps and nothing collapses — but a 700 dp window spends both flanks on chrome that would be free below the frames, and the document describes a screen that does not exist.
**Proposal:** Either implement the portrait arrangement behind the same solver (a `stacked` variant of `threeUpLayout` that returns flank height instead of flank width, chosen by comparing the region's aspect against the frame's), or cut §15.1's claim down to what ships. Do not leave the doc describing the unimplemented half — a specification nobody has built reads exactly like a regression to the next agent measuring the screen.

## [OPEN] 2026-08-07 - Compose UI in `:android-desktop` has no JVM-testable layout layer beyond `FrameGeometry`
**Where:** `products/android/android-desktop/src/com/photoselectortoolbox/ui/selector/`
**Debt:** The selector rewrite extracted its sizing arithmetic into `FrameGeometry`, which is a pure object with a real unit-test suite — and that is the only part of the layout that can be verified without a device. Everything else (overlay placement branches, control-block arrangement, the maximised state) is verified only by instrumented tests, which need an emulator and so are the gate most likely to be skipped. ## 2026-07-27 - The Local Test Runner Enforced a Strict Subset of CI, So "Green Locally" Meant Nothing (extended 2026-08-08)
**Learning:** `scripts/run_tests.sh` — the script every agent doc pointed at as *the* test gate — ran `pytest` and `gradlew testDebugUnitTest` and nothing else. CI ran four gates it did not: flake8 (a **separate job that gates the entire desktop pipeline**, so a lint error fails everything before one test executes), `--cov-fail-under=60`, the `-m "not visual"` split, and `assembleDebugAndroidTest`. An agent could therefore run the sanctioned command, see green, push, and fail CI on a gate it had no way to evaluate. `ai/skills/self_improvement/SKILL.md` Phase 2 asked "did tests pass?" without naming a command, so nothing forced the gap closed. The visible symptom was chains of blind `fix(ci)`/`fix(test)` commits: on `feat/score-chips-and-first-run-hints`, nine consecutive commits, each a guess adjudicated by a 15-minute CI run.
**Action:** A gate that exists only in CI is a gate that cannot be satisfied before pushing. `scripts/run_tests.sh` is now an explicit CI mirror: it runs every workflow gate in the same order with the same flags, and prints a per-gate PASS/FAIL/**SKIPPED** summary mapping each to its CI job. Skipped gates must be named in the task summary rather than silently treated as passes. When you change a gate in `.github/workflows/`, mirror it in `scripts/run_tests.sh` and `docs/build/CI_PARITY.md` **in the same commit**.
**Extended 2026-08-08:** naming a gate SKIPPED is necessary and not sufficient. `connectedDebugAndroidTest` needs a device, so it is skipped on every developer machine and its CI output is read by nobody — it stood **red at `HEAD` for over a week**: four `NavigationTest` cases reaching for a `NavigationRail` the sidebar rewrite had retired, and one asserting a fixed percentage floor that a CI emulator smaller than the reference device can never meet. Every branch in that window paid the same tax, running a baseline in a second worktree to tell its own regressions from the status quo. A gate nobody can run locally decays to red by default, and a permanently red suite trains everyone to stop reading it — the same failure the CI mirror was built to end, one level further out. The first time you run a device-gated suite on a branch, establish the baseline on unmodified `HEAD` **before** believing any failure; file red-at-`HEAD` as its own backlog item rather than absorbing it into your change, and fix it before adding tests to that suite. And write its assertions as functions of the *measured* device, with absolute floors guarded by a device-class predicate — otherwise the gate reports CI hardware as a product defect (`ai/memory/palette.md` 2026-08-08).

## 2026-07-27 - Compose Semantics-Tree Mistakes, Not Compile Errors, Are the Bulk of Emulator-Only CI Thrash
**Learning:** Classifying the nine `fix(test)`/`fix(android)` commits on `feat/score-chips-and-first-run-hints`: exactly **one** (2431d41) was a compile error (`hasTag`→`hasTestTag`, `item.path`→`item.uri`) — the class `assembleDebugAndroidTest` now catches locally. The other **eight** were the same narrow family of semantics-tree errors: `onNode` throwing on multiple matches, missing `useUnmergedTree = true` inside `ModalBottomSheet`, and unscoped `hasText` matching both a chip and a legend row. Adding the compile gate alone would have prevented one of nine commits. The remaining eight were preventable only by convention, because they are runtime behaviours of the Compose semantics tree.
**Action:** Codify the conventions rather than discovering them per-branch (now in `ai/agents/android-desktop-ui-agent.md` rule 9 and `docs/build/CI_PARITY.md`): prefer `onAllNodes(...).onFirst()` over `onNode(...)` for anything that can match more than once; pass `useUnmergedTree = true` when asserting inside a semantics-merging container; scope with `hasAnyAncestor(hasTestTag(...))` instead of bare text; and import Compose test matchers explicitly, never `androidx.compose.ui.test.*`. Instrumented tests legitimately need a device — they assert on a live semantics tree with Hilt injection and a real Activity lifecycle — so they stay in `androidTest`; what changed is that their *compile* failures no longer need one.

## 2026-07-27 - One Coverage Threshold Across Three OS Runners Is a Per-OS Lottery
**Learning:** `desktop.yml` applied `--cov-fail-under=60` on ubuntu, macOS **and** Windows. But `products/desktop/tests/conftest.py` skips by platform (`linux_only`/`mac_only`/`windows_only`) and skips `gui_required` without a display, so each runner executes a different subset and reaches a different coverage number. A change could pass on a contributor's Mac and fail the threshold only on the Windows runner — a CI-only failure with no local reproduction, which is precisely the condition that produces speculative fix commits.
**Action:** Enforce a coverage threshold on exactly one runner (Linux, which executes the largest subset). Other platforms still run the full suite and still fail on real test failures. ## 2026-07-12 - GitHub Actions Workflow Rename Run Number Reset
**Learning:** Renaming or changing a GitHub Actions workflow filename resets the `github.run_number` count back to 1 for that new file. If `github.run_number` is used in version code calculations, the reset causes version code regressions. ## 2026-07-11 - Gradle Kotlin DSL 'java' Collision & GitHub Workflow Resilience
**Learning:** 
1. In Gradle Kotlin DSL, `java` is a reserved keyword referring to the Gradle Java plugin/extension. Referencing fully qualified names starting with `java.` (e.g. `java.util.Properties`) inside build files yields compiler errors like `Unresolved reference 'util'`.
